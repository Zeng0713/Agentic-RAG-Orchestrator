# RAG 搭建流程

## RAG 搭建流程总览

RAG（检索增强生成）系统先从知识库检索与用户问题相关的资料，再将资料和问题交给大语言模型生成回答。搭建一个基础 RAG 系统通常包括以下步骤：

1. 明确系统要回答的问题类型和范围。
2. 加载并解析文档。
3. 将文档切分为片段，并保存来源等元数据。
4. 使用 Embedding 模型把片段转换为向量。
5. 将向量、文本和元数据写入向量数据库，建立可更新的索引。
6. 根据用户问题检索相关片段，可组合关键词检索和向量检索。
7. 将检索结果组织为上下文，交给大语言模型生成有依据的回答。
8. 评估检索结果和回答质量，并根据问题持续调整。

简要链路是：文档加载与解析 → 切分与元数据 → Embedding → 向量存储 → 检索 → 上下文构造与回答 → 评估迭代。重排序、查询改写、多格式文件解析等属于可选扩展，并非基础流程都必须实现。

## RAG 是什么

RAG 是 Retrieval-Augmented Generation 的缩写，中文称为检索增强生成。它将外部知识检索与大语言模型生成结合起来：系统先从知识库找到与问题相关的内容，再把这些内容作为上下文交给模型回答。

RAG 可以让回答参考特定知识库中的资料，并帮助追踪答案依据。但它不能保证答案一定正确；如果资料缺失、检索不相关或内容过时，回答仍可能不可靠。

## 如何明确 RAG 系统的问题范围

搭建前应明确系统要服务哪些用户、回答哪些类型的问题，以及知识库覆盖哪些主题。问题范围会影响文档结构、检索方式、上下文长度和回答规则。

还应确定系统在资料直接包含答案、只能回答部分问题、资料不足或问题超出范围时如何回应。提示词可以要求模型优先依据检索资料、明确说明资料不足，并避免编造没有依据的事实。

## 如何加载和解析文档

文档加载负责读取文件或数据源，并将内容转换为后续流程使用的统一格式。常见格式包括 Markdown、HTML、PDF、Word 文档和数据库记录。

解析时应尽可能保留标题、段落和列表等结构。表格、代码块、扫描件和复杂版式可能需要不同的解析方式。还应发现解析失败或内容为空的文档，避免将无效内容写入索引。

本项目当前通过 `src/document_loader.py` 加载 `data/documents/` 下的 Markdown 文件，并按二级标题 `##` 切分章节。PDF、Word 和扫描件解析不属于当前实现。

## 如何切分文档

文档切分是将较长内容拆成检索片段（Chunk）。检索时通常只把相关片段交给模型，而不是把整个知识库放进提示词。切分效果会影响检索准确度和回答上下文是否完整。

常见切分方法包括：

- **按标题切分**：保留章节边界，适合结构清晰的 Markdown 和技术文档。
- **按段落切分**：尽量保留完整论述，适合段落结构清晰的文章。
- **按固定长度切分**：适合结构不统一的文本，但边界可能截断句子或概念。
- **重叠切分**：让相邻片段共享一部分文字，以保留跨边界的上下文；代价是增加存储量和重复检索。

片段过大可能包含较多无关内容，片段过小则可能缺少必要背景。可以用代表性问题检查召回的内容，再调整切分方式、长度和重叠比例。

## 什么是 Embedding

Embedding 是把文本转换成一组数字的表示，称为向量。语义相近的文本通常会在向量空间中较接近，因此可以用向量相似度查找含义相关的内容。

建立索引时，系统为文档片段生成向量；用户提问时，也使用兼容的 Embedding 模型将问题转换为向量。更换模型可能改变向量空间，因此通常需要重新计算已有文档向量，避免新旧向量无法比较。

本项目使用 SiliconFlow API 上的 `BAAI/bge-m3` 生成向量。

## 向量检索是什么

向量检索会比较问题向量与文档向量的相似程度，并返回最接近的片段。常见计算方法包括余弦相似度、点积和欧氏距离，选择时应符合 Embedding 模型和向量数据库的使用约定。

向量检索适合表达不同但语义相近的查询。不过，语义相近不代表内容可以互换；精确编号、罕见词和专有名称也可能匹配不准。应通过实际问题集检查检索结果，而不能只看分数。

## 什么是向量数据库

向量数据库用于保存向量及其关联的文本和元数据，并支持相似度检索。在 RAG 中，一条记录通常包含向量、知识片段、来源信息和唯一标识。

元数据可以保存来源路径、标题、类别或日期，用于追踪资料和筛选结果。唯一标识有助于识别新增和变化的片段，避免重复写入。

本项目使用本地持久化的 Chroma 保存知识片段。`src/vector_store.py` 当前会新增新片段，并更新内容变化的片段。源文档删除后的旧记录清理，需要另行实现和验证。

## 如何维护向量索引

知识库内容变化时，索引可能需要新增、更新、删除或重建：

- **新增**：将新文档片段及其向量加入索引。
- **更新**：替换内容已变化的记录。
- **删除**：移除源文档已删除或失效的记录。
- **重建**：在切分方式、Embedding 模型或索引配置重大变化时重新生成数据。

应采用稳定的记录标识，并检查更新后是否仍能检索到旧内容。持久化数据也应与源文档、Embedding 模型和索引配置一并管理，才能可靠恢复知识库。

## 什么是混合检索

混合检索是组合多种检索方法来寻找相关资料。RAG 中常见的做法是结合关键词检索和向量检索：关键词检索擅长精确匹配名称、编号和专有术语，向量检索擅长找到措辞不同但语义相近的内容。

组合两者可以兼顾精确匹配和语义匹配，但也可能带入重复或无关结果，因此通常还需要合并、去重和排序。

## 如何进行混合检索

一种简单做法是先进行标题或关键词匹配，再执行向量检索；合并结果时优先保留精确命中的片段，再补入向量搜索结果，并删除重复内容。

更复杂的做法可以融合不同检索器的排名，或使用重排序模型再次排序。不同检索器的相似度分数尺度可能不同，不能未经处理就直接相加。

返回结果数量需要平衡完整性与噪声：数量太少可能漏掉依据，太多则会增加无关上下文并占用模型输入长度。应使用代表性问题检查合并结果是否比单一检索更有帮助。

本项目的 `src/retriever.py` 会优先加入标题关键词匹配结果，再补充 Chroma 向量搜索结果，并限制结果数量、避免重复片段。

## 如何组织上下文并生成回答

检索后，系统将片段和用户问题组织成提示词，交给大语言模型生成回答。上下文应清楚区分不同资料，并保留来源编号或来源元数据。

提示词可以要求模型优先依据资料、指出无法确定的部分、资料不足时明确说明，并只引用实际支持结论的片段。提示词不能弥补错误的检索结果；如果资料不相关或不完整，最终回答也可能出错。

本项目的传统 RAG 流程在 `src/rag_chain.py` 中构造提示词，由 DeepSeek 生成回答，并根据回答实际引用的资料编号整理来源。

## 如何评估 RAG 检索和回答

评估应分别检查检索质量和答案质量。只看回答是否流畅，无法判断系统是否找到正确资料。

可以准备一组代表性问题，为每题记录预期依据，包括直接可回答的问题、多片段问题、同义表达、专有名称查询，以及知识库资料不足的问题。

检索评估关注正确资料是否出现在结果中、排名是否靠前、是否存在重复或无关内容。答案评估关注事实是否有依据、关键条件是否遗漏、引用是否对应正确来源，以及资料不足时是否明确说明。

发现错误时，可依次检查文档是否正确加载、切分是否完整、Embedding 和检索是否找到合适片段、上下文是否保留必要内容，以及模型和引用处理是否正确。调整后使用同一问题集进行回归检查。

本项目目前有离线单元测试，但尚未建立独立的 RAG 检索与回答评估数据集。

## RAG 的可选扩展

基础 RAG 流程可以根据实际效果增加其他能力，但这些都不是必选步骤：

- **元数据过滤**：按来源、时间、类别等条件缩小检索范围。
- **重排序**：使用排序模型对初次检索结果重新排列。
- **查询改写**：将用户问题改写为更适合搜索的表达。
- **多轮对话处理**：结合对话历史理解省略上下文的问题。
- **缓存、日志和监控**：减少重复计算并帮助排查运行问题。
- **权限控制**：限制用户可以查询的知识范围。

应根据评估结果、使用需求和维护成本决定是否加入这些扩展。本项目当前未实现多格式文档解析、重排序和查询改写。
